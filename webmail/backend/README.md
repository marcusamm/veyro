# Veyro webmail API

The Cloudflare Worker forwards same-origin webmail requests to this service on the mail guest. It listens on `127.0.0.1:18082`. Dovecot IMAPS and Postfix submission use local loopback with TLS and the hostname `post.veyro.dk`. Install these files in the root-owned `/etc/veyro-webmail-api` directory and run `sh stage.sh`. The systemd path unit watches mailcow's public certificate. Its one-shot service checks the certificate's validity and hostname, then atomically replaces the API's copy. New IMAP and SMTP connections pick up the new trust file. The API has no access to mailcow's private key.

The Worker must replace the origin and client IP authentication headers with its own `X-Veyro-Origin-Token` secret and the visitor address from Cloudflare. The guest reads its token from `secrets/origin-token`. Preserve the original browser Origin and the session cookie. POST requests require the exact Veyro webmail origin. Authenticated mutations require the session's CSRF token. Forward `Idempotency-Key` for message submissions.

Customers sign in using an active, individually provisioned local mailbox on a hosted Veyro Mail domain with IMAP and webmail access. Customer accounts requiring a native password change or enrollment or verification of a second factor must use native Mailcow access. Staff retain the existing IMAP app-password path and self-service recovery enrollment. Mailcow verifies mailbox credentials. Sessions live in one Gunicorn process, expire after 30 idle minutes or eight hours, and use an opaque HttpOnly, Secure, host-only cookie. Mailbox credentials stay encrypted with a process-local ephemeral key while the session is active. Restarting the container invalidates browser sessions, delegated AI connections and the one-hour submission replay cache.

For an existing installation, run `python3 configure-recovery.py --upgrade-mailbox-view` on the guest when releasing the customer-enabled API. To revert this change, restore the previous API and run `python3 configure-recovery.py --rollback-mailbox-view`. Both commands update only the existing database view used for login and credential revocation.

`POST /api/password` accepts `currentPassword` and `newPassword` from a webmail session using the mailbox's primary password. The service opens a temporary mailbox-user session on the private mailcow HTTPS listener, verifies the native identity and submits mailcow's CSRF-protected self-service form. Mailcow enforces its configured password policy. Veyro limits the new password to the installed bcrypt scheme's 72-byte maximum. Native MFA challenges and incomplete MFA setup require administrator assistance. A successful change, or an interrupted change with an uncertain result, closes all Veyro webmail sessions for that mailbox. The exact outcome of an interrupted change can be checked by signing in again. Separately issued app passwords follow mailcow's own lifecycle.

On the Veyro mail guest, Dovecot must verify the new password immediately on each IMAP or SMTP sign-in. Mailcow's default Dovecot cache can accept the previous password for five minutes. When provisioning this deployment, merge `auth_cache_size = 0` into the mailcow directory's `data/conf/dovecot/extra.conf`, preserving other local settings. From the mailcow directory, validate with `docker compose exec -T dovecot-mailcow doveconf -h auth_cache_size` (expected `0`), then apply with `docker compose exec -T dovecot-mailcow doveadm reload`.

The signed-in recovery enrollment routes require the mailbox's primary password, a valid webmail session and its CSRF token. The mailbox must have the native Mailcow password recovery ACL enabled. The employee receives a 12-character code at the external address and confirms it within ten minutes in the same session. Confirmation saves the address through Mailcow self-service. The signed-out recovery request queues a native Mailcow reset for an allowed mailbox and gives the browser the same reply regardless of enrollment. Configure the native recovery notification sender and subject in Mailcow. Native tokens follow Mailcow's expiry, reuse and additional-factor rules.

Organization administration is available only to `marcus@veyro.dk`. The webmail API checks the signed-in mailbox and verifies its primary password with Mailcow before displaying tenant data. Writes require the current password, the session and its CSRF token. The isolated `org-broker` container handles a fixed set of operations over a private Unix socket. Its native Mailcow key is restricted to local addresses and stored under `/etc/veyro-mail-admin/private` on the guest. Preserve that directory in the protected server backup. The broker can manage Veyro's own domain and hosted domains tagged `veyro-mail-organization`; creating a customer domain requires the matching public TXT challenge. The dashboard makes no changes at the customer's DNS provider.

Each authenticated webmail request checks a mailbox credential version through the local read-only database view `veyro_webmail_credential_version`. The API reads its restricted connection configuration from `/run/veyro/credential-version.json`. The view returns the username and an opaque version. A native password reset changes the version and expires previous Veyro webmail sessions on their next request. A failed version lookup temporarily blocks authenticated requests.

Folder and message IDs are opaque to the frontend. Pagination uses the mailbox UIDVALIDITY and message UID boundaries. Listing reads message metadata. Opening a message retrieves its selected text part and marks it Seen. HTML-only mail is converted to plain text. Attachments are fetched separately with a 32 MiB encoded-part limit. New mail and replies submit through SMTP and add a copy to the IMAP Sent folder. The API accepts text-only compositions and JSON requests up to 256 KiB.
