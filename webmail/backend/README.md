# Veyro webmail API

The Cloudflare Worker forwards same-origin webmail requests to this service on the mail guest. It listens on `127.0.0.1:18082`. Dovecot IMAPS and Postfix submission use local loopback with TLS and the hostname `post.veyro.dk`. Install these files in the root-owned `/etc/veyro-webmail-api` directory and run `sh stage.sh`. The systemd path unit watches mailcow's public certificate. Its one-shot service checks the certificate's validity and hostname, then atomically replaces the API's copy. New IMAP and SMTP connections pick up the new trust file. The API has no access to mailcow's private key.

The Worker must replace the origin and client IP authentication headers with its own `X-Veyro-Origin-Token` secret and the visitor address from Cloudflare. The guest reads its token from `secrets/origin-token`. Preserve the original browser Origin and the session cookie. POST requests require the exact Veyro webmail origin. Authenticated mutations require the session's CSRF token. Forward `Idempotency-Key` for message submissions.

Customers sign in using an active, individually provisioned local mailbox on a hosted Veyro Mail domain with IMAP and webmail access. Customer accounts requiring a native password change or enrollment or verification of a second factor must use native Mailcow access. Staff retain the existing IMAP app-password path and self-service recovery enrollment. Mailcow verifies mailbox credentials. Ordinary sessions live in one Gunicorn process, expire after 30 idle minutes or eight hours, and use an opaque HttpOnly, Secure, host-only, SameSite=Lax browser-session cookie. Mailbox credentials stay encrypted with a process-local ephemeral key while a session is active. Restarting the container invalidates ordinary browser sessions, delegated AI connections and the one-hour submission replay cache.

`POST /api/login` additionally accepts `rememberMe`, strictly a JSON boolean and defaulting to `false`. Choosing **Forbliv logget ind** issues the same opaque cookie with a fixed 30-day Max-Age. Only opted-in sessions persist in `/var/lib/veyro-webmail/remembered-sessions.sqlite3` on the existing `organizer` Docker volume. SQLite stores the token's SHA-256 hash, a keyed mailbox index, an expiry, and a Fernet-encrypted payload containing the server-side IMAP credential, credential generation and CSRF proof. No credentials or tokens enter browser storage or logs. Activity never extends the 30-day expiry. Browser closure and container restarts preserve remembered login, including the CSRF token of a tab that was already open. Idle cached sessions still close their IMAP connections and leave RAM; the next request can rehydrate a valid remembered login. The cache is limited to 128 sessions and durable storage to 1,024 sessions / 20 per mailbox, with expiry cleanup and a database page limit.

`stage.sh` provisions `secrets/remembered-session-key` once, validates but never overwrites it, and sets ownership `root:65532` and mode `0440`; the existing secrets mount exposes it read-only at `/run/veyro/remembered-session-key`. The database is mode `0600` inside the private organizer volume. Preserve the existing key and volume across releases. Back up both privately; the key must be treated as a credential and kept separate from an ordinary database backup. Missing, unreadable or invalid keys fail remembered login/restoration closed with a retryable error. They do not downgrade remembered credentials to plaintext or prevent an otherwise valid ordinary login. No runtime key generation or automatic key rotation takes place.

Logout and replacement login revoke the previous durable token. Password changes/reset, mailbox deactivation or access revocation invalidate remembered logins as well as in-memory sessions. Every restored **and cached** authenticated session checks the current credential version. Administrator role changes revoke sessions before changing the role, so a failed durable revocation cannot grant an older login new privileges. To force a mailbox to sign in again operationally, run on the guest (substitute the intended mailbox):

```sh
cd /etc/veyro-webmail-api
docker compose exec -T api python -c 'from remembered_sessions import Store; Store().delete_account("person@example.test")'
docker compose restart api
```

The restart also retires ordinary in-memory sessions for other mailboxes; their remembered tokens remain valid. Never remove or replace the session key as part of a normal release. Tests use temporary SQLite files and fictional mailbox credentials: `python -m unittest discover -s webmail/backend -p 'test_*.py'` from the repository root with the backend requirements installed (Python 3.12).

For an existing installation, run `python3 configure-recovery.py --upgrade-mailbox-view` on the guest when releasing the customer-enabled API. To revert this change, restore the previous API and run `python3 configure-recovery.py --rollback-mailbox-view`. Both commands update only the existing database view used for login and credential revocation.

`POST /api/password` accepts `currentPassword` and `newPassword` from a webmail session using the mailbox's primary password. The service opens a temporary mailbox-user session on the private mailcow HTTPS listener, verifies the native identity and submits mailcow's CSRF-protected self-service form. Mailcow enforces its configured password policy. Veyro limits the new password to the installed bcrypt scheme's 72-byte maximum. Native MFA challenges and incomplete MFA setup require administrator assistance. A successful change, or an interrupted change with an uncertain result, closes all Veyro webmail sessions for that mailbox. The exact outcome of an interrupted change can be checked by signing in again. Separately issued app passwords follow mailcow's own lifecycle.

On the Veyro mail guest, Dovecot must verify the new password immediately on each IMAP or SMTP sign-in. Mailcow's default Dovecot cache can accept the previous password for five minutes. When provisioning this deployment, merge `auth_cache_size = 0` into the mailcow directory's `data/conf/dovecot/extra.conf`, preserving other local settings. From the mailcow directory, validate with `docker compose exec -T dovecot-mailcow doveconf -h auth_cache_size` (expected `0`), then apply with `docker compose exec -T dovecot-mailcow doveadm reload`.

The signed-in recovery enrollment routes require the mailbox's primary password, a valid webmail session and its CSRF token. The mailbox must have the native Mailcow password recovery ACL enabled. The employee receives a 12-character code at the external address and confirms it within ten minutes in the same session. Confirmation saves the address through Mailcow self-service. The signed-out recovery request queues a native Mailcow reset for an allowed mailbox and gives the browser the same reply regardless of enrollment. Configure the native recovery notification sender and subject in Mailcow. Native tokens follow Mailcow's expiry, reuse and additional-factor rules.

`marcus@veyro.dk` administers all hosted organizations. Marcus can grant or remove the organization administrator role from an eligible mailbox in the employee directory. A delegated administrator can list their own company's mailboxes and create, deactivate or reset the password of an ordinary employee mailbox on that domain. Marcus manages organization setup, DNS, reactivation and other administrators. Each write requires the acting administrator's primary password and the session's CSRF token. Role changes end the affected mailbox's Veyro webmail sessions. An administrative password reset also invalidates delegated AI access and outstanding native recovery links. Independently issued IMAP/SMTP app passwords have their own lifecycle.

The broker receives the authenticated actor over its private Unix socket. It checks the role and domain on every operation. Role assignments are stored in the native mail database and tied to the mailbox. Removing or disabling the mailbox removes its assignment. The dedicated database credential and the local IP-restricted Mailcow API key live in `/etc/veyro-mail-admin/private` on the guest. Back up this directory and the mail database. The broker manages Veyro's own domain and domains tagged `veyro-mail-organization`. Creating a customer domain requires the matching public TXT challenge.

Each authenticated webmail request checks a mailbox credential version through the local read-only database view `veyro_webmail_credential_version`. The API reads its restricted connection configuration from `/run/veyro/credential-version.json`. The view returns the username and an opaque version. A native password reset changes the version and expires previous Veyro webmail sessions on their next request. A failed version lookup temporarily blocks authenticated requests.

Folder and message IDs are opaque to the frontend. Pagination uses the mailbox UIDVALIDITY and message UID boundaries. Listing reads message metadata. The web reader receives a text body, sanitized HTML when available, and the result of the server's message checks. It displays external links without loading remote images. Opening a message marks it Seen. Attachments are fetched separately with a 32 MiB encoded-part limit. New mail and replies submit through SMTP and add a copy to the IMAP Sent folder. The API accepts text-only compositions and JSON requests up to 256 KiB.
